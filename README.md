# Navigation Realty API

FastAPI backend for the Navigation Realty CRM — serves both the Agent Dashboard
and the Client Portal from one API, with RBAC enforced at the router level.

## Local setup

```
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env            # fill in DATABASE_URL, JWT_SECRET, ANTHROPIC_API_KEY
alembic upgrade head            # creates all 14 tables - do this before first run
uvicorn app.main:app --reload
```

API docs: http://localhost:8000/docs

## Project layout

```
app/
  main.py           - FastAPI app, router registration, CORS
  database.py        - SQLAlchemy engine/session
  models.py           - all tables from the schema (agents, contacts, deals, ...)
  schemas.py          - Pydantic request/response models
  auth.py              - JWT issuing + require_agent / require_client dependencies
  routers/
    auth_router.py     - POST /auth/agent/login, POST /auth/client/login
    contacts.py          - agent-scoped CRUD, intake form -> Contact + profile, auto-enrolls new_lead workflows
    deals.py               - pipeline endpoints (list, create, move stage)
    activities.py           - manual ledger entries (calls, notes)
    documents.py             - document hub, status transitions
    showings.py               - schedule showings, log feedback, auto-enrolls post_showing workflows
    workflows.py               - drip campaign config + manual enrollment
    cma.py                      - CMA report generation
    ai_content.py                - Claude-drafted follow-ups/listing copy
    portal.py                     - Client Portal - every query scoped to caller's contact_id
  services/
    mailer.py            - stubbed email/SMS sender + built-in template copy (swap for SendGrid/Twilio)
    enrollment.py          - auto_enroll(): matches a trigger event to the agent's active workflows
    scheduler.py             - APScheduler background jobs that actually fire drip-campaign steps
```

## Workflow scheduler

Drip campaigns run via two APScheduler jobs started on app startup (`app/services/scheduler.py`):

- **`process_enrollments`** (every 15 min) — walks every `active` `WorkflowEnrollment`,
  checks whether the next step is due (`enrolled_at` + cumulative `delay_days`), sends it
  through `mailer.send_message`, logs it to the contact's activity ledger, and advances
  `current_step`. Marks the enrollment `completed` after the last step.
- **`enroll_anniversaries`** (daily at 06:00 UTC) — finds deals that closed ~365 days ago
  and enrolls those contacts into any workflow with `trigger_event="anniversary"`.

Enrollment itself happens automatically at three points, via `services/enrollment.auto_enroll`:
- a new contact is created → `trigger_event="new_lead"`
- showing feedback is logged (`PATCH /showings/{id}/feedback`) → `trigger_event="post_showing"`
- a deal's one-year closing anniversary → `trigger_event="anniversary"`

Set `SCHEDULER_ENABLED=false` in your env to disable the background jobs (useful for local
dev/tests so it isn't ticking every 15 minutes while you work).

Message bodies are currently pulled from a small built-in `TEMPLATES` dict in `mailer.py`
keyed by `template_id`, not generated live — swap this for a real templates table, or pipe
`template_id` through the existing `/ai/generate` endpoint if you want each send to be
freshly AI-drafted (costs a Claude call per send, so weigh that against a static template).

## RBAC model
Two token roles are issued:
- **agent** (or **admin**) - from `/auth/agent/login`. Every agent-facing router
  filters by `current.agent_id` pulled from the JWT, never from the request.
- **client** - from `/auth/client/login`. The `portal.py` router filters every
  query by `current.sub` (the contact's own id) - there is no `contact_id`
  parameter anywhere in that file, so a buyer/seller physically cannot query
  another client's data even by guessing an id.

## Migrations (Alembic)

`migrations/versions/0001_initial.py` creates all 14 tables and matches `app/models.py`
exactly. It's hand-authored rather than autogenerated — the environment this was built
in has no live Postgres to diff against, which is what `alembic revision --autogenerate`
needs. Going forward:
1. Point `DATABASE_URL` at a real (even local/throwaway) Postgres and run
   `alembic revision --autogenerate -m "describe the change"` — this is the normal,
   preferred path once you have a real database to develop against.
2. If you don't have DB access at the moment, you can hand-edit a new revision file the
   same way `0001_initial.py` was written — just make sure it actually matches
   `models.py`, since nothing checks that for you outside of a real autogenerate diff.

Sanity-check any migration before trusting it: `alembic upgrade head --sql` prints the
raw SQL without touching a database, so you can review exactly what would run.

## Deploying to Render

1. This repo pins `.python-version` to `3.11.8` — keep it, newer default
   Python versions on Render currently fail to build some of these packages.
2. Add a managed PostgreSQL instance on Render and set `DATABASE_URL` from it.
3. Set `DATABASE_URL`, `JWT_SECRET`, `ANTHROPIC_API_KEY`, `DOCS_BUCKET`, `AWS_REGION`,
and `ESIGN_WEBHOOK_SECRET` in the Render environment tab (S3 credentials come from
an attached IAM role, or `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` if not on AWS).
4. Start command: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
   — **run this as a single instance/worker.** APScheduler runs in-process; if you scale
   to multiple Render instances or multiple uvicorn workers, each one starts its own
   scheduler and every drip-campaign step fires once per instance. Move to Celery+Redis
   (with a single beat scheduler) before scaling the web service past one instance.
5. Before starting the app for the first time (and after every future schema change),
   run the migration: `alembic upgrade head`. `main.py` no longer calls `create_all` —
   Alembic owns the schema now. On Render, add this as a **pre-deploy command** (or a
   one-off job) rather than the start command, so it runs once per deploy, not once
   per request/restart.

## Document storage (S3)

`app/services/storage.py` uses presigned S3 urls so files never pass through the API
server: the agent (or client, via the portal) requests a presigned PUT url from
`POST /documents/upload-url`, uploads directly to S3 from the browser, then confirms
with `POST /documents` using the same key. Reads work the same way in reverse — every
`DocumentOut` response mints a fresh 15-minute presigned GET url rather than storing
a permanent link, so a leaked API response can't leak permanent file access.

Works against real AWS S3 or any S3-compatible store (Cloudflare R2, Backblaze B2,
MinIO for local dev) — set `S3_ENDPOINT_URL` for anything other than AWS.

## E-signature

`app/services/esign.py` is stubbed the same way the mailer is: `create_envelope()`
simulates a provider response so `POST /documents/{id}/send-for-signature` and the
document hub UI can be built and tested now, without a live DocuSign/HelloSign
account. `POST /documents/esign-webhook` is the receiving end — point your provider's
webhook config at it once you're wired to a real one, and swap the HMAC check in
`verify_webhook_signature` for whatever scheme that provider actually uses (DocuSign
Connect, for instance, has its own signing format — the stub here is illustrative,
not DocuSign's real algorithm).

## Client Portal PWA

The Buyer/Seller Portal front-ends (`BuyerPortal.jsx` / `SellerPortal.jsx`) have a
separate PWA wrapper — manifest, service worker, offline page — that isn't part of
this backend package. See its own README for how it plugs into a Vite build.

## Not yet implemented (next steps)

- **Real provider credentials**: both S3 and e-signature are wired with real
  request/response shapes, but `esign.py` still fakes the actual provider call
  (`create_envelope`) — plug in DocuSign/HelloSign's SDK when you have an account.
- **Alembic migrations**: still using `create_all`, called out above — matters
  more now that there's a schema change (Document no longer stores a raw `file_url`,
  it stores an S3 key) to actually migrate if you have existing data.
- **Push notifications & background sync**: mentioned in the PWA README — not
  covered by this backend or the service worker as shipped.
